# PR作成前のJavadoc確認手順

`docs/javadoc`はコミット対象の生成物で、`src/main`のクラス・メソッド・Javadocコメントの変更に追従して
変わる。再生成を忘れるとPRのドキュメントが古いまま残り、旧クラスのHTMLも残り続ける。
再生成の結果は、ソースの変更と混ざるとレビューしづらいので、**必ず別コミットにする**。

再生成は冪等（ソースが変わらなければ差分は出ない）なので、「再生成して差分があるか」で要否を判定する。

## 手順

1. 作業ツリーに未コミットの変更が残っていないことを確認する（`git status --short`）。
   あるときは、先にソースの変更を通常のコミットにする。
2. `./gradlew javadoc`を実行する。doclintで壊れたJavadoc（タグの誤り・参照先の無いリンク等）も検知されるので、
   失敗したらソース側を直してから、やり直す。
   - Maven Centralから429が返って依存の解決に失敗したときは、少し待ってやり直す。
   - Gradle 8.7はJDK25を認識できない。JDK21に切り替えてから実行する（[verify](../verify/SKILL.md)の前提を参照）。
3. `git status --short docs/javadoc`で差分を確認する。
   - **差分なし**: Javadocの追加は不要。そのままPR作成へ進む。
   - **差分あり**: 次の手順でコミットする。
4. 差分は`docs/javadoc`配下だけであることを確認する。それ以外のファイルが変わっていたら、
   Javadoc再生成の副作用ではないので、内容を確かめてから扱う（混ぜてコミットしない）。
5. `docs/javadoc`だけをステージして、ソースの変更とは別のコミットにする。
   新規ファイル（`??`）と削除（`D`）も含める。

   ```
   git add -A docs/javadoc
   git commit -m "<変更内容>に合わせてdocs/javadocを再生成する"
   ```

   - コミットは、ソースの変更のコミットより**後**に積む。
   - メッセージにはソース側の変更内容を繰り返さず、再生成の理由だけを書く。
6. 直後に`git status --short`が空であることを確認してから、pushしてPRを作成する。

## 注意

- PRの作成は、利用者から依頼されたときだけ行う。この手順は、依頼を受けたあとの準備として使う。
- すでにpush済みのコミットを分け直す場合は、自分が作ったブランチで、PRがまだ無いときだけ
  履歴を書き換えてよい（`git push --force-with-lease`）。他人のブランチやPRが開いているブランチでは、
  履歴を書き換えず、再生成のコミットを積む。
